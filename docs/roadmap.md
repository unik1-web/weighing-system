# Дорожная карта развития

Документ описывает план доработки существующего приложения учёта взвешиваний на полигоне ТКО.
Подход — **эволюция**, а не переписывание: сохраняем стек (React + Flask + SQLite), поставку одним `.exe`, интеграции РЭО и импорт Vescom / Metra / WA.

## Принципы

| Принцип | Решение |
|---------|---------|
| Стек | React + TypeScript, Flask, SQLite, Web Serial — без смены на FastAPI / PostgreSQL / микросервисы |
| Поставка | Два варианта `.exe` (базовый / полный), данные рядом с программой |
| Автоматизация | **Нет.** Оператор всегда подтверждает распознанный номер и данные вручную |
| РЭО, импорт | Сохраняем без изменений контракта |
| Метрология в акте | **Не печатаем** — аттестация весов ежегодная, сертификат рассылается клиентам отдельно |
| Фото водителя | **Не нужно** |
| Ручной ввод веса | Пометка только в базе и журнале, **не на печатной форме** |
| Фото на печати | **Не нужно** — только просмотр на экране |
| Режим работы полигона | Без выходных; все машины покидают полигон к концу рабочего дня |
| Правка архива | **Да**, роль `admin` |
| Сборки установщика | **Две:** базовая (без камер) и полная (с фото/ANPR) |
| Порог ANPR для релиза | **≥ 50%** точности на спайке |
| Камера для номера | **Общий ракурс** (отдельной камеры крупным планом нет) |

## Референс: Vescom StaticTruckScale

На объектах используется Vescom (`C:\Program Files (x86)\Vescom\StaticTruckScale`). Ключевые параметры из `StaticTruckScale.ini`, которые повторяем в настройках:

| Параметр | Значение (пример) | Смысл |
|----------|-------------------|-------|
| `DefaultFirstWeightType` | `2` | Режим взвешивания по умолчанию |
| `StableMode` | `1` | Разрешать фиксацию нестабильного веса |
| `TaraThreshold` | `1` | Порог (т) для автоопределения брутто/тара |
| `MaxTimeBetween` | `60` | Макс. интервал (мин) между двумя проходами |
| `TaraDefault` | `10.0` | Тара по умолчанию (т), если машина не в справочнике |
| `[Video] CameraCount` | `2` | Число камер, RTSP URL |
| `[Recognize] Enabled` | `0` | У Vescom — ISS SecurOS; **у нас — своя локальная модель** |

Два режима работы оператора (как в Vescom):

1. **Одиночное** — один проход на весах, тара из справочника автомобиля (или `TaraDefault`).
2. **Двойное** — первый проход сохраняется как незавершённое взвешивание; второй проход — выбор записи из списка незавершённых и фиксация тары.

## Что уже есть в приложении

Не переписываем — расширяем:

- Абстракция весов: 4 профиля терминалов, Web Serial, универсальный парсер кадра (`src/lib/scales.ts`)
- Журнал, отчёты, печать акта/талона, справочники, пользователи
- Поля `gross_source` / `tare_source` (`manual` | `instrument`) — расширим
- Статус тикета `open` | `completed` — доработаем UX дозавершения
- РЭО, импорт Vescom / Metra / WA, нормализация госномеров

## Этапы

### Этап 1. Два режима взвешивания — ~2 недели

**Цель:** паритет с Vescom по одиночному и двойному взвешиванию.

**Схема данных**

- Поле `weighing_mode: 'single' | 'double'` в тикете и в настройках (режим по умолчанию).

**Одиночное взвешивание**

- Один проход → сразу `status = completed`.
- Тара из карточки автомобиля (`default_tare_weight`); если нет — из настройки `TaraDefault`.
- Источник тары: `dictionary` или `default` (см. этап 2).

**Двойное взвешивание**

- Первый проход → `status = open`, фиксируется брутто.
- Второй проход — панель «Незавершённые»: список open-тикетов, поиск по госномеру, автоподсказка при вводе номера с открытой записью.
- Дозавершение из журнала (сейчас open можно сохранить, но не возобновить).
- Автоопределение брутто/тара по `TaraThreshold` (как в Vescom).
- Предупреждение при превышении `MaxTimeBetween` — при ежедневном закрытии полигона интервал обычно в пределах смены; правило остаётся для контроля ошибок оператора.

**Настройки (новые)**

- `weighing_mode_default`, `stable_mode`, `tara_threshold`, `max_time_between`, `tara_default`.

**Техническое**

- Оптимистичная блокировка (`version`) при обновлении тикета.
- Таблица `ticket_audit`: кто, когда, что изменил (важно при смене оператора между проходами).

**Критерий готовности:** оператор проходит оба сценария без обходных путей; незавершённое взвешивание можно найти и закрыть из формы и из журнала.

---

### Этап 2. Источник веса и пометка ручного ввода — ~3 дня

**Цель:** однозначно видеть в базе, откуда взялся каждый вес.

**Расширение `WeightSource`**

| Значение | Смысл |
|----------|-------|
| `instrument` | С весов (Web Serial) |
| `manual` | Оператор ввёл число с клавиатуры |
| `dictionary` | Тара из справочника автомобиля |
| `default` | Тара из глобальной настройки `TaraDefault` |

**Исправления**

- При автоподстановке тары из справочника не ставить `manual` (текущий баг в `WeighingForm.tsx`).
- Исправить эффект автоподстановки тары: не возвращать значение после ручного сброса оператором.

**UI**

- В форме: бейджи «ПРИБОР» / «РУЧНОЙ» / «СПРАВОЧНИК» / «ПО УМОЛЧАНИЮ» у брутто и тары.
- В журнале: иконка и фильтр «есть ручной ввод».
- В отчётах: сводка по ручному вводу за период (по операторам).

Печатные формы **не меняем**.

**Критерий готовности:** каждый сохранённый тикет имеет корректный источник; фильтр в журнале работает.

---

### Этап 3. Водители по автомобилю — ~1 неделя

**Цель:** при выборе госномера предлагать водителей, которые раньше возили эту машину.

**Схема**

- Таблица `vehicle_drivers`: `vehicle_number`, `driver_name`, `last_used_at`, `use_count`.
- Обновление при каждом сохранении тикета.
- **Переносится в новую годовую базу** при ротации (в отличие от DISTINCT по журналу, который обнуляется 1 января).

**Настройка `driver_input_mode`**

| Режим | Поведение |
|-------|-----------|
| `vehicle` | Сначала водители этой машины; кнопка «все водители» |
| `all` | Общий справочник (как сейчас) |
| `free` | Свободный ввод без подсказок |

- Если у машины один водитель в истории — подставлять автоматически.
- Нормализация ФИО через `formatPersonName` (без дублей «Иванов И.И.» / «Иванов Иван Иванович»).

**Опционально:** первичное заполнение `vehicle_drivers` при импорте справочников из Vescom / Metra / WA.

**Критерий готовности:** выбор водителя для частой машины — 1–2 клика; настройка режима в «Настройках».

---

### Этап 4. Годовая база и архив — ~1,5 недели

**Цель:** рабочая база хранится один календарный год; с 1 января — новая, старая — архив только для чтения.

**Файлы**

- `BD/weighing-2026.db`, `BD/weighing-2027.db`, …
- Текущий год — в `config.ini` (`database_year` или путь к активному файлу).

**Ротация (1 января или при первом запуске после смены года)**

1. Принудительно закрыть все `open`-тикеты в **уходящей** базе:
   - тара = `default_tare_weight` из карточки авто или `TaraDefault`;
   - `tare_source = 'dictionary'` или `'default'`;
   - `auto_closed = 1`, примечание «Закрыто автоматически при смене года».
2. Показать оператору список закрытых записей и запросить подтверждение (не молча).
3. Предупреждение, если среди закрытых есть `reo_status = pending`.
4. Создать новую базу; перенести: справочники, пользователей, настройки, `vehicle_drivers`.
5. Журнал взвешиваний **не переносить**.
6. Резервная копия архивной `.db` в момент ротации.

**Нумерация талонов:** с **1** в каждой новой базе. В UI и на печати — **«№ N от ДД.ММ.ГГГГ»**, чтобы не путать одноимённые номера разных лет.

**Архив**

- Переключатель «Текущий год / Архив ГГГГ» в журнале и отчётах.
- Обычным пользователям: поиск, просмотр, перепечатка акта.
- **Администратор (`admin`):** правка записей в архивной базе (исправление ошибок оператора).
  - Все изменения пишутся в `ticket_audit` (старое/новое значение, кто, когда).
  - Предупреждение, если запись уже отправлена в РЭО (`reo_status = sent`).
  - Перепечатка акта после правки — по запросу оператора.

**Контекст эксплуатации:** полигон работает без выходных, все машины уезжают к концу дня. Незавершённых взвешиваний на ночь быть не должно; ротация закрывает редкие забытые `open`, а не массовый поток «машина стояла с 31.12 по 09.01».

**Критерий готовности:** смена года не теряет справочники и историю водителей по машинам; архив читается; нумерация в новом году с 1.

---

### Этап 5. Фотофиксация — ~2 недели

**Зависимость:** IP-камеры и RTSP на объекте.

**Настройки** (по аналогии с Vescom `[Video]`)

- Включение подсистемы (`video_enabled`), число камер (1–4), RTSP URL, каталог хранения (по умолчанию `Photo/` рядом с программой).
- Камера для ANPR — **та же, что общий ракурс** (отдельного RTSP для номера нет); в настройках указывается, какая из камер используется для распознавания.

**Поведение**

- Снимок в момент фиксации веса (брутто / тара) со **всех** включённых камер.
- Для ANPR (этап 6) — кадр с выбранной камеры общего ракурса; опционально ROI (зона номера) в настройках для стабильного кадрирования.
- Путь: `Photo/ГГГГ/ММ/ДД/<ticket>_<camera>_<pass>.jpg`.
- Таблица `ticket_photos`: привязка к тикету, камера, тип прохода, путь, timestamp.
- Хранение: JPEG 1280×720, quality ~75 (~45 ГБ/год при ~200 машинах/день, 2 прохода, 2 камеры).
- Удаление фото вместе с архивом года (или копирование в архивный каталог при ротации).

**Техника**

- OpenCV, фоновый поток с постоянным RTSP; по событию — последний кадр.
- Внутри процесса Flask, без отдельного сервиса.

**UI**

- Превью в форме взвешивания и в карточке записи журнала.
- На печать **не выводим**.

**Сборки**

| Сборка | Состав | Когда ставить |
|--------|--------|---------------|
| **Базовая** | Этапы 1–4, без OpenCV и моделей | Объект без камер |
| **Полная** | Базовая + фото + ANPR | Объект с IP-камерами |

Внутри **полной** сборки подсистема фото включается переключателем в настройках (`video_enabled`, как `[Video] Enabled` в Vescom) — без переустановки программы.

**Критерий готовности:** после сохранения тикета видны снимки с камер; при недоступности камеры взвешивание не блокируется.

---

### Этап 6. Распознавание госномера (ANPR) — спайк + ~2 недели

**Зависимость:** этап 5 (кадр с камеры общего ракурса).

**Принцип:** только подсказка оператору, **без автоматического принятия**.

**Поток**

1. Оператор фиксирует вес (или нажимает «Распознать»).
2. Кадр с камеры общего ракурса (при необходимости — обрезка по ROI) → локальная модель (детектор + OCR).
3. Результат в поле госномера: подсветка «предложено», confidence, миниатюра кадра.
4. Оператор подтверждает (Enter / Tab) или исправляет вручную.

**Сохранение в тикете**

- `anpr_plate_raw`, `anpr_confidence`, `anpr_accepted` (bool).
- Подстановка в справочник — только после подтверждения; fuzzy-match лишь предлагает кандидатов, не подставляет молча.

**Спайк (до основной разработки, ~1 неделя на объекте)**

- 50–100 реальных кадров с **общего ракурса**: день / ночь / дождь / грязные номера.
- Замер точности на **ваших** данных.
- **Порог для включения в релиз: ≥ 50%** (доля кадров, где распознанный номер совпал с эталоном без правки оператора).
- Если на спайке < 50% — ANPR остаётся выключенным по умолчанию; ручной ввод номера без изменений.

**Ограничения общего ракурса**

- Номер занимает малую долю кадра — детектор должен находить область номера на всём изображении.
- Качество ниже, чем у отдельной камеры крупным планом; 50% — осознанный минимум при human-in-the-loop.
- Настройка ROI (прямоугольник зоны номера на превью) снижает ложные срабатывания.

**Критерий готовности:** на спайке ≥ 50%; в UI всегда есть ручной ввод; оператор видит confidence и кадр перед подтверждением.

---

### Отдельно: безопасность учётных записей — ~3–4 дня

Не блокирует этапы 1–4, желательно до передачи заказчику.

- Заменить `btoa` на нормальное хэширование паролей на сервере.
- Смена дефолтного пароля `admin` / `admin123` при первом входе.

## Сводный график

| Этап | Срок | Результат для оператора |
|------|------|-------------------------|
| 1. Два режима | ~2 нед. | Одиночное и двойное взвешивание как в Vescom |
| 2. Источник веса | ~3 дн. | Видно, где вес с прибора, где руками |
| 3. Водители по авто | ~1 нед. | Быстрый выбор водителя для знакомой машины |
| 4. Годовая база | ~1,5 нед. | Новый год — новая база, старая в архиве |
| 5. Фото | ~2 нед. | Снимки к записи на экране |
| 6. ANPR | спайк + ~2 нед. | Подсказка номера с подтверждением |
| Безопасность | ~3–4 дн. | Пароли не в base64 |

**Этапы 1–4:** ~5 недель — полностью рабочий продукт без камер.  
**Этапы 5–6:** +3–4 недели после появления камер и успешного спайка.

Оценка для **1–2 разработчиков**; каждый этап — отгружаемая версия.

## Что сознательно не делаем

- Микросервисы, PostgreSQL, MinIO, RabbitMQ, PySide6 / Electron
- Шлагбаум, RFID, автоматический пропуск без оператора
- Метрологические реквизиты в акте
- Фото водителя, фото в печатной форме
- Интеграция с ISS SecurOS Auto (своя локальная модель)
- Автообновление тары в справочнике по последнему взвешиванию

## Принятые решения (2026)

| Вопрос | Решение |
|--------|---------|
| Правка архивных записей | Да, только `admin`, с аудитом и предупреждением при отправке в РЭО |
| Сборки | Две: базовая и полная; в полной — переключатель `video_enabled` в настройках |
| Порог ANPR | ≥ 50% на спайке; иначе функция выключена по умолчанию |
| Камера для номера | Общий ракурс; ROI в настройках для зоны номера |
