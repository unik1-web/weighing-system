# Roadmap: универсальная весовая программа

Документ опирается на текущее состояние репозитория `weighing-system` и на уточнённую модель площадки (основные / резервные весы, независимые камеры, ANPR как опциональный источник номера).

Стек остаётся прежним: **React (Vite) + Flask + SQLite + config.ini**, Windows-сборка через PyInstaller. Новые подсистемы (камеры, ANPR, адаптеры терминалов) наращиваются поверх существующего учёта взвешиваний, а не заменяют его.

---

## 1. Текущее состояние (as-is)

### Уже есть

| Область | Реализация | Где |
|--------|------------|-----|
| Журнал взвешиваний | `WeighingTicket`, CRUD через localStorage → SQLite | `src/lib/storage.ts`, `server/sqlite_store.py` |
| Источник веса | `gross_source` / `tare_source`: `manual` \| `instrument` | талон + форма |
| Ручной ввод веса | поля брутто/тара на форме | `WeighingForm.tsx` |
| Терминалы (частично) | Web Serial, 4 фиксированных профиля | `src/lib/scales.ts`, `ScalePanel.tsx`, `useScale.ts` |
| Справочники | авто, водители, грузы, контрагенты | `DictionaryManager`, импорт Vescom/Metra/WA |
| Подстановка по номеру | только марка и стандартная тара | `WeighingForm.tsx` |
| Нормализация госномеров | латиница→кириллица, регион по умолчанию 56 | `vehicle-plate.ts`, `dictionary_import.py` |
| Печать / РЭО / отчёты | акт, талон, CSV, интеграция РЭО | `PrintAct`, `reo.ts`, `ReportsView` |
| Аудит веса (частично) | raw-кадр, datetime, имя модели в `scale_device` | талон; в журнале/CSV почти не показывается |

### Чего нет

- модель **площадки** с основными и резервными весами;
- реестр **терминалов** и pluggable-адаптеров протоколов (есть только 4 hardcoded Web Serial-профиля и один глобальный `ScaleConnection`);
- **камеры**, снимки до/после, хранение файлов;
- **ANPR** и статусы `enabled` / `disabled_by_configuration` / `failed`;
- автоподстановка **ФИО водителя, груза, грузоотправителя** по номеру;
- переключатель активного комплекта весов с политикой камер/ANPR;
- полный аудит талона (экземпляр весов, источник номера, фото, режим камер, журнал исправлений).

Миграции в `supabase/migrations/` — исторический черновик схемы; runtime использует локальный SQLite. Камер и multi-scale там тоже нет.

## 2. Целевая модель (to-be)

Сущности **независимы**: весы, камеры и ANPR не жёстко связаны. Связь задаётся конфигурацией площадки и активным режимом.

```text
Весовая площадка
├── Основные весы  (терминал + адаптер протокола)
├── Резервные весы (опционально)
├── Камера 1 — въезд / общий план
├── Камера 2 — выезд / общий план
└── Режим (active_scale_set):
    ├── primary  → фото + ANPR
    └── spare    → только фото, номер вручную
                   (камеры повёрнуты оператором)
```

### Принципы

1. **Резервные весы** — полноценное оборудование, не «неисправные». Переключение фиксируется с причиной и оператором.
2. **ANPR** — один из способов получить номер, не обязательное условие автоподстановки справочников.
3. На резервных весах распознавание **не запускается** (ложный номер опаснее его отсутствия).
4. После ввода/выбора номера программа всегда подтягивает связанные поля из справочника / последнего рейса.
5. Каждое взвешивание доказуемо: какие весы, какой источник веса и номера, какие снимки, какой режим камер.

## 3. Целевая схема данных (эскиз)

### Площадка и оборудование

```text
sites
  id, name, notes

scales
  id, site_id, role (primary|spare), name,
  adapter_id, connection (COM/TCP/… JSON),
  terminal_id_label, is_enabled

cameras
  id, site_id, name, role (entry|exit|overview),
  capture_url / device, reference_shot_primary_path,
  reference_shot_spare_path

site_runtime
  site_id, active_scale_set (primary|spare),
  switched_at, switched_by, switch_reason,
  camera_mode, anpr_mode
```

`anpr_mode` на уровне runtime:

| Значение | Когда |
|----------|--------|
| `enabled` | основные весы, подходящий ракурс |
| `disabled_by_configuration` | резервные весы / политика площадки |
| `failed` | ожидалось распознавание, номер не найден |

### Связи справочника «Авто»

Расширить запись ТС (или отдельную таблицу предпочтений / «последний рейс»):

- `preferred_driver_id` / ФИО;
- `preferred_cargo_id` / название;
- `preferred_shipper_id` / название;
- `vehicle_brand`, `default_tare_weight` (уже есть).

Автоподстановка: номер → марка, тара, водитель, груз, грузоотправитель. Оператор может переопределить любое поле.

### Талон (расширение `WeighingTicket`)

Добавить к существующим полям:

| Поле | Назначение |
|------|------------|
| `site_id` | площадка |
| `scale_id` | конкретные весы |
| `scale_role` | `primary` \| `spare` |
| `scale_terminal_id` | идентификатор терминала в талоне |
| `weight_source` / уже есть per gross/tare | терминал или ручной ввод |
| `manual_weight_reason` | причина ручного ввода |
| `plate_source` | `anpr` \| `operator` \| `directory` |
| `plate_confidence` | уверенность ANPR (nullable) |
| `anpr_status` | `enabled` \| `disabled_by_configuration` \| `failed` \| `not_applicable` |
| `camera_mode` | режим на момент взвешивания |
| `photo_gross_before`, `photo_gross_after` | пути к файлам |
| `photo_tare_before`, `photo_tare_after` | пути к файлам |
| `camera_ids` | какие камеры снимали |
| audit log исправлений | отдельная таблица `ticket_revisions` |

Файлы снимков: каталог рядом с приложением, например `BD/photos/{ticket_id}/…`, не внутри `_MEIPASS`.

## 4. Фазы работ

### Фаза 0 — Фундамент учёта и автоподстановки  
*Без нового железа; опирается на текущий UI*

**Цель:** закрыть пробелы справочников и аудита, которые уже можно сделать на существующем стеке.

- Расширить модель авто: предпочтительные водитель / груз / грузоотправитель (и опционально перевозчик).
- На форме взвешивания при выборе/вводе номера подставлять ФИО, марку, груз, грузоотправителя, тару.
- Запоминать «последний рейс» по номеру (обновлять предпочтения при завершении талона).
- Добавить в талон и SQLite заготовки полей аудита (`scale_role`, `plate_source`, пути фото — nullable).
- Показывать в карточке талона / CSV: источник веса, устройство, оператор (сейчас почти скрыто).
- Сохранять выбранную модель весов в настройках (сейчас только session state в форме).

**Критерий готовности:** оператор вводит номер из справочника → поля заполняются; ручной ввод веса и instrument-захват работают как раньше; миграция SQLite без потери журнала.

---

### Фаза 1 — Модель площадки и переключение основных / резервных весов

**Цель:** независимая конфигурация комплектов весов и явный runtime-режим.

- Сущности `sites`, `scales`, `site_runtime` в SQLite + UI в настройках.
- Минимум одна площадка «по умолчанию» при миграции (текущее одиночное подключение → primary).
- Переключатель в UI оператора: «Основные» / «Резервные», причина (ремонт, очистка, поверка, другое), подтверждение.
- При переключении меняются: активный терминал, профиль протокола, `scale_id`/`scale_role` в новых талонах, `anpr_mode`, `camera_mode`.
- Wizard при уходе на резерв:
  1. Поверните камеру въезда  
  2. Поверните камеру выезда  
  3. Сверьте live-кадр с эталонным снимком (когда появятся камеры — фаза 3)  
  4. Подтвердите переход  
  5. Вводите номер вручную  
- Пока камер нет — шаги 1–3 как чеклист с подтверждением оператора.

**Критерий готовности:** талон всегда знает, на каких весах взвешивали; переключение пишется в runtime-журнал; на spare ANPR помечается `disabled_by_configuration` даже до внедрения распознавания.

---

### Фаза 2 — Универсальные адаптеры весовых терминалов

**Цель:** подключение «к любому терминалу» через реестр адаптеров, а не hardcoded switch.

Текущее: `SCALE_DEVICES` + один `parseFrame()` + singleton Web Serial.

Целевое:

```text
ScaleAdapter
  id, name
  connect(config) / disconnect()
  read(): ScaleReading | stream subscribe
  supports: serial | tcp | http | sdk
```

- Вынести Микросим / Ньютон / CAS / Мидл в отдельные адаптеры.
- Добавить адаптер «произвольный разбор» (regex / маска кадра) для новых терминалов без кода.
- Параметры соединения хранить в `scales.connection`, не в UI-only state.
- **Решение по I/O:** оставить Web Serial для Chrome/Edge на одном ПК; параллельно заложить backend-прокси (`pyserial` / TCP) в Flask (`/api/scales/*`), чтобы:
  - работали несколько портов (primary + spare без переподключения вручную);
  - не зависеть только от браузерного Serial;
  - exe-сборка могла держать соединение на стороне процесса.
- Ручной ввод веса сохраняется всегда; при ручном вводе — обязательная/опциональная причина (настраиваемо).

**Критерий готовности:** новая модель терминала подключается конфигом или тонким адаптером; активный комплект площадки выбирает нужный адаптер; weight source в талоне корректен.

---

### Фаза 3 — Камеры и фотофиксация (независимо от ANPR)

**Цель:** снимки до и после на первом и втором взвешивании, хранение в БД/ФС.

- Реестр камер площадки (не привязан жёстко к конкретным весам).
- Backend: захват кадра (HTTP snapshot URL, RTSP→кадр, или vendor API — адаптер `CameraCapture`).
- API: `POST /api/cameras/{id}/snapshot`, раздача/скачивание файлов из `BD/photos/`.
- На форме: превью двух камер; при фиксации брутто/тары — автосохранение before/after (политика: 1 или 2 кадра на событие — уточняется UX).
- Эталонные снимки ракурса primary/spare для сравнения при переключении.
- В режиме spare: фотофиксация **доступна**, ANPR **выключен**.
- Просмотр снимков в карточке талона и при печати (ссылка / вложение по необходимости).

**Критерий готовности:** у завершённого талона есть пути к снимкам; файлы переживают перезапуск; отсутствие камеры не блокирует взвешивание (graceful degrade).

---

### Фаза 4 — ANPR и единый пайплайн «номер → справочники»

**Цель:** распознавание как опциональный вход; три состояния; без ложных номеров на резерве.

```text
[Камера] → [ANPR adapter] → plate + confidence
                ↓
     anpr_mode == enabled?
        нет → operator/directory input
        да  → accept / reject by threshold
                ↓
         resolveVehicle(plate)
                ↓
    driver, brand, cargo, shipper, tare
```

- Адаптер ANPR (локальный сервис / HTTP к коробочному распознавателю).
- Пороги уверенности; ниже порога → `failed`, ручной ввод.
- `plate_source`: `anpr` | `operator` | `directory`.
- На `disabled_by_configuration` движок **не вызывается**; в отчётах это не ошибка оборудования.
- UI: подтверждение распознанного номера одним действием; правка без сброса автоподстановки связанных полей по желанию оператора.

**Критерий готовности:** на primary успешный ANPR заполняет форму; на spare путь только ручной/справочник; отчёты различают «выключено конфигом» и «сбой распознавания».

---

### Фаза 5 — Политика режима, аудит, отчёты, печать

**Цель:** эксплуатационная доказуемость и удобство смены комплекта.

- Единый «режим площадки» в шапке формы взвешивания (primary/spare, ANPR on/off, статус камер).
- Журнал переключений комплекта весов.
- `ticket_revisions` — кто менял номер, веса, контрагентов после сохранения.
- Журнал / фильтры / CSV / акт-талон: площадка, весы, источники, наличие фото.
- Инструкция и эталоны камер встроены в wizard (см. фазу 1).
- Документация: обновить `docs/architecture.md`, `docs/api.md`, README.

**Опционально позже:** отдельная длиннофокусная камера для ANPR на резервных весах — подключается как ещё одна камера с `anpr_enabled=true` в режиме spare, без ломки модели.

| Новое | Предлагаемое место |
|-------|-------------------|
| Модель площадки / runtime | `server/sqlite_store.py`, `src/lib/storage.ts`, настройки |
| Адаптеры весов | `src/lib/scales/` + опционально `server/scale_adapters/` |

## 6. Порядок внедрения и зависимости

```text
Фаза 0  автоподстановка + поля аудита
   │
Фаза 1  площадка + primary/spare runtime
   │
   ├──────────────┬──────────────┐
Фаза 2 терминалы  Фаза 3 камеры  │
   │              │              │
   └──────┬───────┘              │
          │                      │
       Фаза 4 ANPR ◄─────────────┘
          │
       Фаза 5 отчёты / аудит / docs
```

Фазы 2 и 3 можно вести параллельно после фазы 1. Фаза 4 зависит от камер (источник кадра) и от runtime `anpr_mode` (фаза 1).

## 7. Риски и ограничения

| Риск | Митигация |
|------|-----------|
| Web Serial — один порт, только Chromium | Backend serial/TCP с фазы 2 |
| Ложный ANPR на повёрнутых камерах | Жёсткий `disabled_by_configuration` на spare |
| Нет автопроверки угла камеры | Эталонные снимки + чеклист оператора |
| Раздувание SQLite бинарниками | Файлы на диске, в БД только пути |
| Миграция существующих талонов | Nullable новые поля; default site + primary |
| Разный `localStorage` у Vite vs Flask | Как сейчас: рабочий контур — `127.0.0.1:5001` |

## 8. Критерии «универсальной» программы (Definition of Done)

Система считается соответствующей целевой архитектуре, когда:

1. На площадке настраиваются основные и (опционально) резервные весы и две общие камеры.
2. Подключается терминал через адаптер или конфиг разбора кадра; вес также вводится вручную с фиксацией источника.
3. Активный комплект переключается явно; на резерве ANPR отключён конфигом, фото сохраняются.
4. Номер приходит из ANPR, от оператора или из справочника — после этого подставляются ФИО, марка, груз, грузоотправитель.
5. В талоне и отчётах видны площадка, весы, источники веса и номера, снимки, режим камер, оператор и история правок.

---

## 9. Ближайший практический шаг

Начать с **фазы 0**: схема предпочтений ТС + автозаполнение формы + заготовки audit-полей в `WeighingTicket` / SQLite. Это даёт сразу заметный эффект оператору и готовит контракт данных для фаз 1–4 без покупки камер и без смены способа подключения весов.
