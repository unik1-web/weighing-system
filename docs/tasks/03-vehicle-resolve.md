# Постановка: автоподстановка по номеру и водители

## Цель

При выборе/вводе госномера заполнять реквизиты рейса за 1–2 действия оператора (марка, тара, ФИО, груз, грузоотправитель) на основе предпочтений ТС, последнего рейса и истории водителей; настроить режим ввода водителя; заложить nullable audit-поля под площадку/фото/ANPR.

Источник требований: [docs/roadmap.md](../roadmap.md), этап 3.  
Зависимости: этапы 1–2 ([01-weighing-modes.md](01-weighing-modes.md), [02-weight-source.md](02-weight-source.md)).

## Контекст as-is

- Подстановка по номеру: в основном марка и стандартная тара (`WeighingForm`).
- Нет таблицы `vehicle_drivers`, нет `driver_input_mode`.
- Нет модуля `vehicle-resolve` / полной цепочки предпочтений ТС + последний рейс.
- Audit-поля площадки/ANPR/фото в тикете отсутствуют (или частично после этапа 1 — только `version` / create-complete audit).
- Модель весов в настройках: один активный Web Serial-профиль; сохранение выбранной модели — уточнить as-is и довести.

Стек: [docs/project-for-agents.md](../project-for-agents.md), [docs/architecture.md](../architecture.md), [docs/api.md](../api.md).

## Что сделать

### Resolve по номеру

- При выборе/вводе номера: марка, тара (с корректным `WeightSource` этапа 2), ФИО водителя, груз, грузоотправитель.
- Источники подстановки (приоритет зафиксировать в ТЗ): предпочтения ТС → последний завершённый рейс этой машины → разумные дефолты.
- Оператор может править любое поле после подстановки; подтверждение не блокирует сохранение.

### Водители

- Таблица / сущность `vehicle_drivers`: история водителей по машине (`last_used_at`, `use_count`); переносится при будущей годовой ротации (этап 6) — схема должна это учитывать.
- Настройка `driver_input_mode`: `vehicle` | `all` | `free`.
  - `vehicle` — список с приоритетом по истории машины;
  - `all` — полный справочник водителей;
  - `free` — свободный ввод строки.
- Один водитель в истории → автоподстановка; иначе — выбор из списка.

### Импорт (опционально в рамках этапа)

- Первичное заполнение `vehicle_drivers` / предпочтений при импорте Vescom/Metra/WA — если не раздувает скоуп; иначе явный follow-up в ТЗ.

### Audit stubs в талоне

Nullable заготовки (без UI камер/ANPR):

- `plate_source` (`anpr` | `operator` | `directory` — на этапе 3 обычно `operator` / `directory`);
- `scale_role` (nullable до этапа 4);
- пути/ссылки на фото (nullable до этапа 7).

### UI / отчёты / настройки

- Показ источника веса, устройства весов и оператора в карточке тикета и CSV.
- Сохранение выбранной модели весов в настройках (`config.ini`).

## Вне скоупа

- Переключение primary/spare, камеры, ANPR-движок.
- Годовая ротация файлов БД (этап 6) — только совместимость схемы `vehicle_drivers`.
- Полный UI правки архива admin.

## Критерии приёмки

- [ ] Частая машина заполняется за 1–2 действия (номер → подстановка ключевых полей).
- [ ] `driver_input_mode` настраивается и влияет на UI выбора водителя.
- [ ] История `vehicle_drivers` обновляется при завершении рейсов.
- [ ] Корректный `WeightSource` для автотары (связь с этапом 2).
- [ ] Nullable audit-поля присутствуют в модели/синхронизации и не ломают старые тикеты.
- [ ] Карточка/CSV показывают источник веса, устройство, оператора.
- [ ] Выбранная модель весов сохраняется в настройках.
- [ ] Регрессии: режимы single/dual, журнал, печать, РЭО, импорты.
- [ ] Тесты на resolve-приоритеты и режимы водителя.
