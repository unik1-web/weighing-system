# Постановка: поиск камеры по IP / бренду / учётке (настройки)

## Цель

Во вкладке настроек **«Камеры и фото»** добавить подраздел **«Поиск камеры»**: интерфейс для ввода IP, наименования (бренда) камеры из выпадающего списка, логина и пароля; окно превью найденного снимка; логика подбора рабочего URL захвата по известным шаблонам. Если наименование не выбрано — перебор по всем известным шаблонам.

Источник: запрос заказчика после этапа 10 (вкладки настроек, HTTP/RTSP камеры).  
Зависимости: этап 7 (фотозахват / `capture_url`), UI настроек камер (вкладка «Камеры и фото»).

## Контекст as-is

- В настройках камера задаётся вручную полем «URL захвата» (HTTP snapshot или RTSP); оператор часто знает только **IP, логин, пароль**, но не RTSP/snapshot-path.
- Типовые URL зависят от бренда (Hikvision, Dahua, Axis, Uniview и т.д.); перебор вручную трудоёмок.
- Уже есть preview снимка (`/api/cameras/snapshot`) и типы `http_snapshot` / `rtsp` / `auto`.
- HTTP snapshot предпочтительнее для провески (без OpenCV); RTSP — запасной вариант при наличии OpenCV.

Стек: [docs/project-for-agents.md](../project-for-agents.md), [docs/architecture.md](../architecture.md), [docs/api.md](../api.md), README (раздел камер).

## Что сделать

### 1. UI: подраздел «Поиск камеры» внутри «Камеры и фото»

- В настройках, на вкладке **«Камеры и фото»**, добавить внутреннюю навигацию/подвкладки (или эквивалент):
  - существующий реестр камер / эталоны (как сейчас);
  - **«Поиск камеры»** — новый экран.
- На экране поиска:
  - **IP** (обязательно; IPv4, опционально порт — по умолчанию 80 для HTTP, 554 для RTSP-кандидатов);
  - **Наименование камеры** — выпадающий список брендов/моделей из каталога шаблонов + пункт «Неизвестно / перебор»;
  - **Логин**, **Пароль**;
  - кнопка **«Найти»** / **«Проверить»**;
  - индикатор прогресса (какой шаблон пробуется, N из M);
  - **окно превью** успешного снимка;
  - список/карточка найденных рабочих URL (HTTP и/или RTSP) с возможностью **подставить** в выбранную камеру реестра или создать новую (роль, имя — по желанию оператора).
- Не хранить пароль в `localStorage` дольше сессии поиска без явного сохранения в `capture_url` выбранной камеры; в логах не писать пароль открытым текстом.

### 2. Каталог шаблонов и логика поиска

- Завести расширяемый каталог известных шаблонов (минимум):
  - **Hikvision** — HTTP ISAPI/Streaming picture; RTSP `Streaming/Channels/101` и субпоток `102`;
  - **Dahua** — HTTP `cgi-bin/snapshot.cgi`; RTSP `cam/realmonitor?channel=1&subtype=0|1`;
  - **Axis** — HTTP `axis-cgi/jpg/image.cgi`;
  - **Uniview** (или аналог) — распространённый HTTP snapshot path;
  - общие fallback: `snapshot.jpg`, `/cgi-bin/snapshot.cgi`, базовые RTSP `/stream1`, `/h264`.
- Подстановка `user`/`password` в URL (percent-encode спецсимволы).
- Если бренд выбран — пробовать только его шаблоны (сначала HTTP, затем RTSP при наличии OpenCV).
- Если бренд **не выбран** («перебор») — идти по всему каталогу в разумном порядке (популярные HTTP → остальные HTTP → RTSP).
- Успех = получен валидный JPEG (или кадр RTSP) через существующий путь захвата; показать превью и зафиксировать рабочий `capture_url` + рекомендуемый `capture_kind`.
- Таймауты на попытку короткие (порядка connect/read как у snapshot); общий wall-clock на весь перебор с возможностью **Отмена**.
- Параллелизм ограниченный (не DDoS камеру): 1–2 одновременных HTTP-попытки; RTSP — последовательно.

### 3. Backend API (предпочтительно)

- Эндпоинт(ы) поиска, например:
  - `POST /api/cameras/discover` — тело: `ip`, `username`, `password`, `brand?`, опции порта;
  - ответ: список кандидатов `{ url, kind, brand, ok, error? }` и/или первый успешный + путь к tmp-preview;
  - либо streaming/progress через несколько коротких запросов / poll — на усмотрение архитектора, но UX должен показывать ход перебора.
- Переиспользовать `grab_frame` / snapshot; не дублировать небезопасный SSRF без ограничений (только частные/локальные сети или явный allow — зафиксировать в architecture).
- Не коммитить боевые URL с паролями в репозиторий и тесты.

### 4. Документация

- README / раздел камер: как пользоваться «Поиск камеры», таблица поддерживаемых брендов, что делать если ничего не найдено (ручной URL, ONVIF/VLC).
- Кратко в `docs/api.md` — контракт discover.

## Вне скоупа

- Полноценный ONVIF Device Discovery (WS-Discovery) по всей подсети (можно отметить как follow-up).
- Авторизация Digest-only без Basic в URL — если не заработает шаблон, честное сообщение; отдельный Digest-клиент — опционально, не блокер MVP.
- Сканирование произвольного интернета / чужих подсетей.
- Смена стека камер (только HTTP/RTSP как сейчас).

## Критерии приёмки

- [ ] Во вкладке «Камеры и фото» есть подраздел **«Поиск камеры»** с полями IP, бренд (select), логин, пароль, превью.
- [ ] При выбранном бренде поиск идёт по шаблонам этого бренда; при успехе видно изображение и рабочий URL.
- [ ] При «Неизвестно / перебор» выполняется перебор каталога с прогрессом и отменой.
- [ ] Найденный URL можно применить к камере в реестре (или создать камеру) без ручного копирования длинного path.
- [ ] Пароли не светятся в логах; тесты без реальных секретов (моки HTTP).
- [ ] README обновлён; регрессии: существующий ручной URL и snapshot в реестре камер не сломаны.

## Ограничения

- Не коммитить боевые RTSP/HTTP URL с паролями, бинарники `Photo/`, секреты.
- Не менять стек; артефакты пайплайна в `docs/{task_id}/` или `docs/implementation/`.
- Уважать таймауты и нагрузку на камеру при переборе.
